Define the customer job and the release decision

Start with a workflow people already use. For the fictional inbox pilot, agree on the mailbox, the replies it may prepare, the evidence each promise needs and the approval required before sending. The PM owns requirements, priority and intended outcomes. An FDE works with the customer on deployment, integrations and observable behavior; the team agrees on its actual ownership split. When a connector misses a policy update, inspect the trace, fix the cause and add a regression case. Bring recurring failures back to Product as reusable improvements. OpenAI and Anthropic role descriptions support this customer-delivery and product-feedback connection, with company-specific scope. For adoption, choose a bounded pilot and compare completed replies, correction effort and repeated use with the existing workflow. Agree on pause conditions and support ownership before expansion. The practice section turns these decisions into requirements and interview-preparation artifacts.

Live slide 02Live slide 03

A language model builds a reply through token predictions.

A language model builds a reply through token predictions.

A large language model (LLM) learns patterns from training examples. In autoregressive generation, it uses those learned patterns and the current context to choose each next token: a word, word fragment or other processing unit.

  1. 01 / Encode — Convert the request into the model's tokens.
  2. 02 / Predict — Estimate possible next-token probabilities from the context.
  3. 03 / Select — Choose a token using the model's generation settings.
  4. 04 / Continue — Add it to the sequence and repeat until a stopping condition.

This mechanism can produce fluent summaries and explanations. Their factual support still needs to be established.

Simplified account of autoregressive text generation. Tokenization and supported modalities vary by model.

A context window gives the request a finite working space.

A context window gives the request a finite working space.

Context is the information available during generation. Instructions, conversation history and tool material consume tokens too. In this illustrative 16,000-token combined budget, the input uses 13,000 and the response has 3,000 reserved.

MaterialTokensWhat it contributes
Instructions and question1,000The task and expected behavior
Recent conversation2,000Prior decisions and relevant history
Tool definitions and results1,000Available operations and their evidence
Selected documents9,000Information needed for the answer
Response allowance3,000Space for the generated reply

Budget for the whole request and response. A larger window increases capacity; choosing useful evidence remains a separate job.

Invented arithmetic, not a model specification. Actual input, output and reasoning limits have model-specific accounting. Bytes and tokens are different units.

RAG supplies relevant evidence before the answer is generated.

RAG supplies relevant evidence before the answer is generated.

Retrieval-augmented generation (RAG) combines information retrieval with an LLM. The application finds relevant source material and includes it in the generation request, so the answer can use information beyond the model's training.

  1. 01 / Prepare — Make documents searchable; retain source identifiers and permissions.
  2. 02 / Retrieve — Find passages relevant to the user's question.
  3. 03 / Assemble — Supply the question, selected passages and answer instructions.
  4. 04 / Generate — Produce a response using the supplied evidence.
  5. 05 / Inspect — Check that the answer is supported and citations resolve.

Evaluate the evidence retrieved and the answer generated: either stage can fail.

Preparation can happen before a request; retrieval and generation happen for the task. RAG itself grants no access rights or accuracy guarantee.

Fine-tuning adapts a pretrained model using task-specific training.

Fine-tuning adapts a pretrained model using task-specific training.

A pretrained model already has learned capabilities. Fine-tuning uses additional training data or feedback to adapt its behavior for a particular job, such as consistent classification, formatting or response preferences.

  1. 01 / Establish — Measure a baseline with the base model and a clear prompt.
  2. 02 / Prepare — Collect representative examples or reliable feedback.
  3. 03 / Adapt — Train a candidate model using the selected method.
  4. 04 / Evaluate — Compare candidates on held-out tasks, quality and cost.

Choose fine-tuning when the behavior gap and available supervision justify training and maintenance effort.

Conceptual method, not a recommendation for a currently available vendor service. Current facts can still be retrieved at runtime.

An agent selects its next action using feedback.

An agent combines a model, tools and task state. A tool is a callable operation such as search, calculation or updating a record. State preserves progress; observations from executed tools inform the next choice.

  3. 03 / Execute — The application checks permission and runs the tool.
  4. 04 / Observe — Return the result or error to the task state.
  5. 05 / Stop or repeat — Finish, escalate, or return to Choose using the new evidence.

A plan proposes actions. Tool execution and feedback establish what actually happened.

Build evals around observable success

An eval joins a starting case, an attempted task and a rule for judging the evidence. Use it before rollout, after a meaningful system change and when a reviewed failure exposes a missing case. Public benchmarks make the test design concrete. ARC-AGI-1 task 67a3c6ac asks the solver to infer a grid transformation; in this selected task, every row is reflected left to right. Success requires exact dimensions and cells. AndroidWorld's MarkorCreateNote asks an agent to save a named note; its grader checks the file and applies a tolerant text match. The classroom shopping.md / Buy milk parameters are an authored instance, with no recorded execution. These tests show different capabilities and different blind spots. The three Hugging Face resources below cover arithmetic, passage-based answering/abstention and checkable instructions. Our inbox product still needs its own supported-reply, permission, retry and outcome cases. Calibrate graders and keep fresh cases outside development.

An eval checks the evidence produced by a task attempt.

An eval checks the evidence produced by a task attempt.

An evaluation turns a product expectation into a repeatable test. A task or case specifies the starting situation, inputs and expected behavior. A trial is one execution of that case; repeated trials reveal variation.

  1. Case — Define the request, initial environment and success criteria.
  2. Trial — Run the system once and retain its messages, tool calls and resulting state.
  3. Grader — Apply a test or rubric to the trace, output or final environment outcome.
  4. Outcome — Inspect what actually changed: a booking confirmation should correspond to a reservation record.

Check the final outcome as well as the conversation. The evaluation harness organizes trials and grading; the agent harness runs the agent.

Repeat the cases where a mistake has a consequence.

Repeat the cases where a mistake has a consequence.

A failure slice is a meaningful subset of cases, such as revoked access or ambiguous feedback. Review both frequency and the harm caused when that slice fails. An overall score can conceal rare, costly mistakes.

Repeated trials · Ask the reliability question explicitly.

Run the same case repeatedly in isolated, reset environments. pass@k asks whether at least one of k attempts succeeds; pass^k asks whether all k succeed. A product that offers one attempt needs a different interpretation from one with safe retries.
